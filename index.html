Introduction

Sun Programming Language

Sun is a general-purpose systems programming language designed particularly for the needs of robotics and AI. It provides Rust-style memory safety, a familiar syntax, and classic concepts such as classes and interfaces. The design optimizes for performance and intelligibility, for human programmers as well as AI coding agents. Sun additionally aims to improve software distribution, especially in robotics applications, by making it easier to package and distribute portable, systems-level software modules.

Hello World

main.sun
using std;
 
/** Runs the example that prints a greeting. */
function main() void {
  println("Hello, Sun!");
}
 
manifest {
    libraries: ["stdlib.moon"]
}

Run directly with JIT:

sun main.sun
Hello, Sun!

Or compile to a native executable:

sun -c -o main main.sun
./main
Hello, Sun!

This is examples/00-hello/ (opens in a new tab), compiled and run in CI — the source above is read straight from that folder.

Design Goals

  • Fast: Systems-level performance without runtime overhead
  • Memory safe: No undefined behavior via Rust-style borrow checking
  • Readable: Straightforward for humans (and AI agents) to read and understand
  • Unambiguous: Sun minimizes alternative syntaxes and hidden control flow such as operator and constructor overloading. There are no hidden memory allocations, no implicit copies of compound values, and no macros.
  • Modular: Sun makes it simple to package and distribute pre-compiled modules (called moon libraries). Source files and dependencies are declared in a manifest block, directly in the source code, making the Sun compiler its own build system. Sun can download dependencies directly from your private GitHub and other platforms, making a centralized package manager unnecessary (though one could still be useful for hosting "trusted" packages.)
  • Designed for Robotics: Robotics software typically involves dozens to hundreds of processes that run across one or more compute nodes and communicate over a DDS (opens in a new tab) using some kind of pub-sub middleware (e.g. ROS (opens in a new tab)). The standard message serialization format is protobuf, which Sun provides built-in support for. A custom DDS and middleware are on the roadmap.
  • Designed for AI: NumPy-like N-D matrices and linear algebra are provided in the standard library. Built-in support for hardware accelerators/GPUs using LLVM Offload is on the roadmap.
⚠️

These are goals and not claims about the language's current capabilities.

Installation

Ubuntu (Debian Package)

Download and install the latest development build:

curl -fL https://github.com/namo-robotics/sun/releases/download/dev/sun_0.dev_amd64.deb -o /tmp/sun_0.dev_amd64.deb && chmod 0644 /tmp/sun_0.dev_amd64.deb
sudo apt install /tmp/sun_0.dev_amd64.deb && rm -f /tmp/sun_0.dev_amd64.deb

Using /tmp lets APT's restricted _apt user reach the package even when your home directory is private. Setting mode 0644 also handles restrictive user umasks.

The package installs sun and sun-lsp to /usr/bin and includes bundled libraries installed to /usr/lib/sun. To update, download and install the new package.

macOS (Apple Silicon)

Install with Homebrew:

brew install namo-robotics/sun/sun

That installs sun, sun-lsp, the standard library and the TLS bundle, and pulls in llvm@20 — the compiler's one runtime dependency. Update with brew update && brew upgrade sun.

Uninstalling

To uninstall the Debian package:

sudo apt remove sun
sudo apt autoremove

To uninstall on macOS:

brew uninstall sun

Build from Source

# Clone the repository
git clone https://github.com/namo-robotics/sun.git
cd sun
./build.sh

On Linux this expects clang, LLVM 20 dev packages, Ninja and lld. On a Mac, install the dependencies with Homebrew first — brew install llvm@20 ninja ccache — and ./build.sh picks up Homebrew's LLVM by itself. Protobuf is built into the compiler from a pinned source release (so every platform compiles the same version); building offline instead needs libprotoc-dev and -DSUN_BUNDLED_PROTOBUF=OFF.

Quick Start

The rest of this page works through the main.sun program from Hello World above.

JIT Execution

To compile and run a Sun program in one go, with just-in-time (JIT) compilation, pass the sun compiler a single .sun file containing a manifest block:

sun main.sun
Hello, Sun!

Compile to native executable

sun -c -o main main.sun
Compiling: main.sun -> main
Successfully compiled to: main
./main
Hello, Sun!

Debug Mode

Use --debug to generate artifacts for debugging the compiler itself:

sun --debug main.sun
Hello, Sun!
Debug output folder: main_debug/
  Generated: main_debug/ast.dot
  Generated: main_debug/scope_tree.html
  Generated: main_debug/ir.ll

This creates:

  • ast.dot — GraphViz visualization of the AST
  • ir.ll — the LLVM IR for the program's own code
  • scope_tree.html — HTML visualization of semantic scopes

The IR keeps only what this file compiled to; the stdlib it calls into is filtered out:

main_debug/ir.ll
; LLVM IR (user-defined only)
; Generated in debug mode - library and imported symbols filtered out
 
@str = private unnamed_addr constant [12 x i8] c"Hello, Sun!\00", align 1
define void @main() {
entry:
  call void @"$5b663db4$_std_println$static_ptr_u8_"(%static_ptr_struct { ptr @str, i64 11 })
  ret void
}

The $5b663db4$ prefix on println marks it as coming from a library bundle; the hash keys the bundle, so two moons can define the same name without colliding.

Visualize the AST:

dot -Tpng main_debug/ast.dot -o ast.png

Manifests

Sun programs and libraries declare their dependencies using a manifest block, written in the source file itself:

manifest {
    source_files: ["utils.sun", "math.sun"]  // All source files except for the one containing this manifest block
    libraries: [
        "stdlib.moon",                       // Found via SUN_PATH
        {                                    // Fetched once, then cached
            url: "https://example.com/libs/mylib.moon",
            hash: "c2e6500466f386836814c860fffcd6fe3dc3f236230746ac977c07c82290613e" // Optional
        }
    ]
    target: { // Target-specific files
        linux: {
            source_files: ["platform_linux.sun"]
            archives: ["vendor/libfoo-linux.a"]
        }
        macos: {
            source_files: ["platform_macos.sun"]
            archives: ["vendor/libfoo-macos.a"]
        }
    }
}

Paths are resolved relative to the source file, then via SUN_PATH. A library given as a url is downloaded with curl on first use and reused from the cache afterwards; the optional hash is the bundle's SHA-256, and a file that does not match it is rejected. A target block takes the same sections as the manifest itself and applies only when compiling for that operating system — the manifest never picks the target, --target (or the host) does. archives are static C libraries carried inside a bundle built with --emit-moon, so whoever imports it links them without needing -l flags.

Path variables

A manifest entry can name a directory with $NAME, so the manifest stays portable when a dependency sits somewhere different on each machine:

manifest {
    libraries: ["stdlib.moon", "$LIBS/mathlib.moon"]
}

Give the value on the command line with --path-var, or let it fall back to a plain environment variable:

sun --path-var LIBS=libs main.sun
LIBS=libs sun main.sun

Committing the value to a Sun config instead means nobody has to remember the flag. A variable defined nowhere is a compile error naming the ways to define it.

Modules and Manifests covers private GitHub assets, rename, and the rest.

Sun Config

A sun-config.json file records the settings a project would otherwise pass on every sun invocation. The compiler looks for one beside the entrypoint and in every folder above it:

sun-config.json
{
    "sun_path": ["../../build"],
    "path_variables": { "LIBS": "libs" },
    "entrypoints": [
        { "path": "stdlib/stdlib.sun", "type": "library",
          "output_name": "build/stdlib",
          "test_binary_name": "build/stdlib_test" }
    ],
    "root": true
}

The supported keys are:

  • sun_path — extra directories to search for .moon libraries, on top of SUN_PATH and the install location
  • path_variables — values for the $NAME variables a manifest uses
  • entrypoints — the project's build products. Each entry names an entrypoint file (path, required), whether it is a "binary" (an executable, the default) or a "library" (a .moon bundle), and optionally what to call the compiled artifact (output_name) and its test binary (test_binary_name). With entrypoints declared, the config file itself can stand in for an entrypoint on the command line — sun -c sun-config.json builds every product, sun test sun-config.json runs every suite — and editor tooling knows the project's entrypoints without scanning
  • target — settings selected by the compilation target (see below).
  • root — true stops the upward search at this file, keeping a project self-contained

Every config from the entrypoint's folder upwards is merged: the nearest definition of a variable wins, search directories and entrypoints are concatenated nearest-first, and a relative path resolves against the folder of the file that declares it. So a workspace root can set shared values once while a subfolder overrides only what is local to it.

A config wins over --path-var and over the environment, which is the opposite of the usual precedence — a checked-in file is meant to be the project's answer, not something a stray shell variable can quietly change.

Cross-compiling configured entrypoints

Pass --target to choose the target triple for every entrypoint built by that invocation. Without it, Sun builds for the host using its matching target settings:

sun -c --target aarch64-linux-gnu --no-test sun-config.json

Here --no-test skips building test binaries. Cross-compiling executables also requires a linker and system libraries for the target.

Installed bundles are selected automatically from target subdirectories such as /usr/lib/sun/aarch64-linux-gnu. Debian packages include AArch64 Linux standard-library and TLS bundles for GNU and musl target spellings.

Each dependency moon must have been built for the selected architecture and operating system, including stdlib.moon. Keep moons for different targets in separate directories and point sun_path at the directory for the build, for example "sun_path": ["libs/aarch64-linux-gnu"]. --target does not append the triple to sun_path or path_variables values, and an existing moon found there is not replaced by one from --lib-path.

A config can declare a complete entrypoint list alongside each target's search paths and fixed path variables:

{
    "root": true,
    "target": {
        "x86_64-linux-gnu": {
            "sun_path": ["build"],
            "path_variables": {"OPENSSL": "vendor/x86_64"},
            "entrypoints": [{
                "path": "app.sun",
                "output_name": "build/app"
            }]
        },
        "aarch64-linux-gnu": {
            "sun_path": ["build/aarch64-linux-gnu"],
            "path_variables": {"OPENSSL": "vendor/aarch64"},
            "entrypoints": [{
                "path": "app.sun",
                "output_name": "build/aarch64-linux-gnu/app",
                "test_binary_name": "build/aarch64-linux-gnu/app_test"
            }]
        }
    }
}

Target keys are normalized LLVM triples: aarch64-linux-gnu and aarch64-unknown-linux-gnu select the same settings. Vendor spellings are ignored; arm64 and aarch64 match the same architecture, and macOS version suffixes do not affect selection. GNU and musl config keys remain distinct. Duplicate normalized keys and invalid settings are errors, including in inactive target blocks.

A matching target replaces sun_path and entrypoints when those fields are present, and merges its path_variables over the defaults in that file. An omitted field keeps its default; an empty entrypoint list selects no entrypoints from that file. Target entrypoints use the same fields as default entrypoints, including path, type, output_name, and test_binary_name. There are no per-entrypoint target blocks.

Configs still merge nearest-first, and config values still take precedence over command-line and environment path variables. Paths remain relative to the file declaring them. Without --target, the host target is selected. If no target block matches, only the top-level settings apply. Paths are otherwise literal; the compiler does not automatically append a target directory.

The workspace root config keeps all settings inside target blocks, including the native platforms. Its AArch64 Linux blocks build stdlib and TLS separately from the native outputs.

Moons

Moons (.moon files) are precompiled library bundles containing compiled code and type information. Create a moon from any .sun file containing a manifest:

mylib.sun
public module mylib {
    public function helper() i32 { return 42; }
}
 
manifest {
    source_files: ["utils.sun", "math.sun"]
}
sun --emit-moon -o mylib.moon mylib.sun

A moon is linked into whatever imports it, so a compiled program carries the moons it uses — nothing to install beside the binary, and nothing to load at run time.

C libraries follow the same preference: sun -c links statically by default, preferring musl where it is installed, and produces one self-contained executable. Dynamic linkage is still available — --dynamic links against shared objects, which vendor SDKs shipped only as .so files need, and macOS targets are always dynamic because Apple ships no static libSystem. See C FFI for the details.
