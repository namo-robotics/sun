# Modules and Manifests

A **module** groups names and controls visibility. A **manifest** lists the files
and libraries compiled with an entrypoint. A **Moon library** (`.moon`) packages
compiled Sun code for another program to use.

Use modules to organize code, manifests to connect files, and the
[build system](/build-system) to build and distribute projects.

## Modules

### Module declarations

Declare a module, then qualify its public names with the module name:

```sun filename="main.sun"
/** Small arithmetic helpers. */
public module math {
  /** Returns the square of a number. */
  public function square(x: i32) i32 { return x * x; }
}

/** Uses a module's public function. */
function main() i32 { return math.square(3); }
```

Run this with `sun main.sun`. Inside `math`, the same function can be called as
`square(3)`.

Dotted declarations create nested modules:

```sun
/** Helpers for reading files. */
public module app.files.readers {}
```

This makes `app`, `files`, and `readers` public. Use separate nested declarations
when each module needs its own documentation.

### Using statements

`using` lets you omit a module prefix. With `math` from the previous example:

```sun
using math;

/** Calls a function without its module prefix. */
function main() i32 { return square(3); }
```

A `using` applies to its file, or to the function or module containing it and
that scope's children. Each source file needs its own `using` statements.
It does not load files or libraries; a manifest does that.

### Visibility

Declarations inside a module are private unless marked `public`:

```sun
/** Number operations available to callers. */
public module numbers {
  /** Doubles an input for use inside this module. */
  function twice(x: i32) i32 { return x * 2; }

  /** Returns four times the input. */
  public function four_times(x: i32) i32 { return twice(twice(x)); }
}
```

Callers can use `numbers.four_times(3)`, but not `numbers.twice(3)`.
Private names are accessible within their module and its children, including
parts of that module in other files. Class members follow the same boundary;
`using` does not bypass it. There is no `private` keyword.

Declarations of the same module must agree on visibility. Names outside any
module are available throughout the program.

### Module-level variables

A module can hold state shared by its callers:

```sun
/** Counts calls for the lifetime of the program. */
public module counter {
  public var count: i64 = 0;

  /** Records one call. */
  public function add() void { count += 1; }
}
```

`counter.add()` changes `counter.count`. Use `const` for values that cannot
change, and protect shared mutable state with a [mutex](/threads) across threads.

## Manifests

An entrypoint's manifest lists additional compilation inputs. For example,
put `math` from above in `math.sun`, and use it from a separate entrypoint:

```sun filename="main.sun"
/** Calls a function from another source file. */
function main() i32 { return math.square(3); }

manifest {
  source_files: ["math.sun"]
}
```

`sun main.sun` compiles both files. Source paths are relative to the entrypoint's
directory. All manifest fields are optional.

### Test files and other inputs

Add only the inputs the entrypoint needs:

```sun
manifest {
  libraries: ["sun/stdlib"]
  test_files: ["math_tests.sun"]
}
```

| Field | Purpose |
| --- | --- |
| `source_files` | Compile additional Sun files. |
| `test_files` | Include files only when compiling [tests](/testing). |
| `libraries` | Load compiled `.moon` libraries. |
| `protos` | Generate types from [Protobuf](/protobuf) schemas. |
| `archives` | Carry native static libraries inside a `.moon` bundle; see [C FFI](/c-ffi). |

For example, `protos: ["messages.proto"]` adds a schema, and
`archives: ["native/libhelper.a"]` adds a native archive.

### Platform-specific files

Use `target` to select extra inputs for the compilation target:

```sun
manifest {
  source_files: ["files.sun"]
  target: {
    linux: { source_files: ["files_linux.sun"] }
    macos: { source_files: ["files_macos.sun"] }
  }
}
```

Linux includes `files_linux.sun` before `files.sun`; macOS uses `files_macos.sun`
instead. `windows` is also supported. `--target` selects the compilation target;
without it, Sun uses the host platform.

### Package library references

A library reference names a package and its entrypoint:

```sun
manifest {
  libraries: ["sun/stdlib", "example/math/math"]
}
```

The last slash separates package ID `example/math` from entrypoint `math`.
Declare external packages in [project dependencies](/build-system#dependencies).
The configuration controls their versions, local providers, and target settings;
Sun resolves their libraries from the installed `lib` directory.

`sun/stdlib` and `sun/tls` use compiler-supplied libraries without fetching a
compiler checkout. A reference to the current package needs no self-dependency,
but the consuming entrypoint must list the library in
[`requires`](/build-system#products-and-build-order) so it is built first.

### Path Resolution

Use a file path for a standalone prebuilt library:

```sun
manifest {
  libraries: ["libs/shapes.moon", "stdlib.moon"]
}
```

Sun searches the entrypoint's directory, config `sun_path` directories,
`--lib-path` directories, `SUN_PATH`, then compiler installation directories,
in that order. For example:

```sh
sun --lib-path /path/to/libraries main.sun
```

### Path variables

Define a directory once in the project configuration:

```json filename="sun-config.json"
{
  "root": true,
  "path_variables": { "LIBS": "vendor" }
}
```

Then use it in a manifest path:

```sun
manifest {
  libraries: ["$LIBS/shapes.moon"]
}
```

Variables expand before path resolution; undefined variables are errors.
Relative config paths resolve against the declaring config. Sun reads configs
from the entrypoint's directory upward until `root: true`; nearer variable
definitions win, and nearer search directories are searched first.

Override a value for one invocation with `sun --path-var LIBS=other main.sun`.
Command-line values override configs, which override editor defaults and the
environment.

## Precompiled libraries (.moon)

Moon files contain compiled code and the metadata needed to import it.

### Creating Moon files

A library exposes public top-level modules:

```sun filename="shapes.sun"
/** Helpers for measuring shapes. */
public module shapes {
  /** Returns the area of a square. */
  public function square_area(side: i32) i32 { return side * side; }
}

manifest {}
```

```sh
sun --emit-moon -o shapes.moon shapes.sun
```

Put library globals inside modules too. Private helpers stay hidden from importers.

### Using Moon files

List the compiled library, then call its public functions:

```sun filename="main.sun"
/** Uses a compiled library. */
function main() i32 { return shapes.square_area(4); }

manifest {
  libraries: ["shapes.moon"]
}
```

Run with `sun main.sun`. This uses the compiled library without needing its source.

### Library identity

The library's identity is independent of its output filename:

```sh
sun --emit-moon --id geometry -o shapes.moon shapes.sun
```

For direct compilation, the local ID defaults to the source filename without
`.sun`; `--id` overrides it. Configured builds use the entrypoint's `name` and
reject `--id`, including in custom builds. A project `package_id` prefixes that
name: package `example/shapes` and entrypoint `geometry` produce identity
`example/shapes/geometry`.

Keep the identity stable when publishing new versions. Renaming a published
entrypoint can break consumers. Identity does not guarantee ABI compatibility,
and source manifests cannot declare an `id`.

### Libraries that use other libraries

For `app → ui.moon → graphics.moon`, an app calling only UI functions needs just
`ui.moon` in its manifest. The UI bundle carries the code and metadata it needs.

To name graphics types directly, also list `graphics.moon`. Importing another
version does not replace the copy inside UI. Sun checks identity and
[ABI compatibility](/abi/compatibility) when values cross library boundaries.

### Module aliases

Give two versions different lookup names:

```sh
sun main.sun --moon shapes-v1.moon:shapes=old_shapes \
    --moon shapes-v2.moon:shapes=new_shapes
```

Source can now use `old_shapes` and `new_shapes`. Aliases change lookup names,
not type identity or compatibility. They also work with package references.

### Library globals and constants

Compile-time constants remain available to importers:

```sun
/** Shared dimensions. */
public module limits {
  public const ROWS: i64 = 3;
}
```

An importer can use `limits.ROWS` as an array size. Values computed at startup
cannot be used that way. Library globals initialize once, before globals in
code that imports them.

### Bundle version names

Add a readable label when producing a library:

```sh
sun --emit-moon shapes.sun -o shapes.moon --version-name v1.0.0
```

The label changes the bundle hash but does not select versions or change
compatibility rules.

### Installed libraries

```sun
manifest {
  libraries: ["sun/stdlib", "sun/tls"]
}
```

The compiler automatically finds the [standard library](/stdlib) and
[TLS library](/tls); TLS carries its OpenSSL dependency. Keep your own bundles
beside the project or add their directory with `--lib-path`.
