# Modules and Manifests

A module groups names. A manifest lists the files and libraries a program uses.

## Module declarations

```sun
/** Small arithmetic helpers. */
public module math {
    /** Returns the square of a number. */
    public function square(x: i32) i32 {
        return x * x;
    }
}

/** Uses a function from another module. */
function main() i32 {
    return math.square(3); // 9
}
```

Inside `math`, call `square(3)` directly. Outside it, use `math.square(3)`.

Dotted names create nested modules:

```sun
/** Helpers for reading files. */
public module app.files.readers {
}
```

This makes `app`, `files`, and `readers` public. The comment documents `readers`.
Use separate nested declarations to document each module.

## Using statements

```sun
using math;

/** Calls square without the module prefix. */
function main() i32 {
    return square(3);
}
```

`using math` lets this file use names from `math` without the prefix. It does
not load another file or library; the manifest does that.

A `using` inside a function or module applies only there and in its children.
Each source file needs its own `using` statements, even when several files
contribute to the same module.

## Visibility

```sun
/** Number operations available to callers. */
public module numbers {
    /** Private helper used within this module. */
    function twice(x: i32) i32 { return x * 2; }

    /** Returns four times the input. */
    public function four_times(x: i32) i32 { return twice(twice(x)); }
}
```

Callers can use `numbers.four_times(3)`. They cannot use `numbers.twice(3)`.

Declarations are private unless marked `public`; there is no `private` keyword.
Private names are accessible within their module and its children, including
parts of that module in other files. `using` does not bypass privacy.

Class members follow the same module boundary. All declarations of the same
module must agree on its visibility. Names outside any module are available
throughout the program.

## Module-level variables

```sun
/** Counts calls for the lifetime of the program. */
public module counter {
    public var count: i64 = 0;

    /** Records one call. */
    public function add() void { count += 1; }
}
```

`counter.add()` changes the shared `counter.count`. Use `const` for a value that
cannot change. Protect shared mutable values with a [mutex](/threads) when using
multiple threads.

## Manifests

```sun filename="main.sun"
using std;

/** Prints a greeting. */
function main() void {
    println("Hello!");
}

manifest {
    source_files: ["helpers.sun"]
    libraries: ["stdlib.moon"]
}
```

Run it with `sun main.sun`. Sun compiles `helpers.sun` with `main.sun` and loads
`stdlib.moon`. Paths start at the directory containing `main.sun`.

Every manifest field is optional. A program with no dependencies can omit the
manifest.

### Test files and other inputs

```sun
manifest {
    test_files: ["helpers_tests.sun"]
    protos: ["messages.proto"]
    archives: ["native/libhelper.a"]
}
```

| Field | Use |
| --- | --- |
| `source_files` | Compile more Sun files with the entrypoint. |
| `test_files` | Include these files only when compiling tests. |
| `libraries` | Load compiled `.moon` libraries. |
| `protos` | Generate message types from Protobuf schemas. |
| `archives` | Carry native static libraries inside a `.moon` bundle. |

See [Testing](/testing), [Protobuf](/protobuf), and [C FFI](/c-ffi) for examples.

### Platform-specific files

```sun
manifest {
    source_files: ["files.sun"]
    target: {
        linux: { source_files: ["files_linux.sun"] }
        macos: { source_files: ["files_macos.sun"] }
    }
}
```

A Linux build includes `files_linux.sun` before `files.sun`. A macOS build uses
`files_macos.sun` instead. `windows` is also supported.

`--target` selects the build target; without it, Sun uses the host platform.
The manifest only selects inputs for that target.

### Path Resolution

```sun
manifest {
    libraries: ["libs/shapes.moon", "stdlib.moon"]
}
```

Sun searches in this order:

1. The entrypoint's directory.
2. `sun_path` directories from its `sun-config.json` files.
3. Directories passed with `--lib-path`.
4. Directories in `SUN_PATH`.
5. The compiler's library installation directories.

An installed compiler finds `stdlib.moon` without extra settings. To use a
library elsewhere:

```sh
sun --lib-path /path/to/libraries main.sun
```

## Precompiled libraries (.moon)

A `.moon` file contains compiled code and the type information needed to use it.

### Creating Moon Files

```sun filename="shapes.sun"
/** Helpers for measuring shapes. */
public module shapes {
    /** Returns the area of a square. */
    public function square_area(side: i32) i32 { return side * side; }
}

manifest {
    id: "example/shapes"
}
```

```sh
sun --emit-moon -o shapes.moon shapes.sun
```

Top-level modules in a library must be public. Put library globals inside a
module too.

### Using Moon Files

```sun filename="main.sun"
/** Uses the compiled shapes library. */
function main() i32 {
    return shapes.square_area(4); // 16
}

manifest {
    libraries: ["shapes.moon"]
}
```

```sh
sun main.sun
```

Private library helpers remain hidden from callers.

### Library identity

```sun
manifest {
    id: "example/shapes"
}
```

Keep this ID when publishing new versions of the same library. The ID identifies
the library; it does not set the output filename or guarantee compatibility.

### Libraries that use other libraries

```text
app → ui.moon → graphics.moon
```

If the app only calls UI functions, its manifest needs only `ui.moon`. The UI
bundle carries the code and metadata it needs from `graphics.moon`.

To name graphics types directly in app source, also list `graphics.moon`.
Using another version does not replace the copy inside `ui.moon`. Sun checks
identity and ABI compatibility when values cross library boundaries; matching
type names alone are not enough. See [ABI compatibility](/abi/compatibility).

### Module aliases

```sh
sun main.sun --moon shapes-v1.moon:shapes=old_shapes \
    --moon shapes-v2.moon:shapes=new_shapes
```

Use `old_shapes` and `new_shapes` in source to distinguish the versions. Aliases
change lookup names, not type identity or compatibility.

### Library globals and constants

```sun
/** Shared dimensions. */
public module limits {
    public const ROWS: i64 = 3;
}
```

An importer can use `limits.ROWS` as an array size because its value is known at
compile time. A constant computed at startup cannot be used that way.

Library globals initialize once, before globals in code that imports them.

### Bundle version names

```sh
sun --emit-moon shapes.sun -o shapes.moon --version-name v1.0.0
```

This adds a readable label. It changes the bundle hash, but does not select
versions or change compatibility rules.

## Downloaded dependencies

### Download a library

```json filename="sun-config.json"
{
  "dependencies": [
    {
      "package": "example/shapes",
      "library": "example/shapes",
      "url": "https://example.com/shapes.moon",
      "hash": "<sha256>"
    }
  ]
}
```

Replace the example URL and `<sha256>` with the library's URL and lowercase
SHA-256 digest. Reference the downloaded library in your manifest:

```sun
manifest {
    libraries: ["${example/shapes}/lib/shapes.moon"]
}
```

With `hash`, Sun reuses matching downloads and rejects changed bytes. Without
`hash`, it downloads the URL each time it resolves the dependency. A failed
download does not fall back to an older cached copy.

### Use a local file, tool, or package

Each example below is one item in the `dependencies` array:

```json
{ "package": "example/shapes", "library": "example/shapes", "path": "vendor/shapes.moon" }
```

`path` is relative to the config file.

```json
{ "package": "example/tools", "binary": "example/viewc", "url": "https://example.com/viewc" }
```

The tool appears at `${example/tools}/bin/viewc`. Use either `library` or
`binary`, never both.

```json
{ "package": "example/tools", "url": "https://example.com/tools.tar.gz" }
```

Omit both to download a whole Sun package. A local `path` may also point to an
extracted package with a verified `package.json`.

For source dependencies, see [Git dependencies](/#sun-config).

### Git repositories

Build selected products from a Git repository:

```json
{
    "dependencies": [
        {
            "git": "git@github.com:example/toolkit.git",
            "version": "v1.2.3",
            "packages": {
                "example/core": {"entrypoints": ["core"]},
                "example/ui": {"entrypoints": ["widgets", "viewc"]}
            }
        }
    ]
}
```

Each config owns at most one `package_id`. A repository root can instead list
`projects` whose configs own different packages. Package IDs must be unique in
that graph. The dependency's `packages` dictionary selects those IDs and names
the library or binary entrypoints to build. Lists must be nonempty and contain
unique names. An optional `config` selects the repository-relative root config;
it defaults to `sun-config.json`.

Import `"${example/core}/lib/core.moon"` in the consumer's manifest. Sun builds
selected products and their prerequisites with a shared repository build root,
runs their preparation steps and custom scripts, and stages each package in its
own directory. Dependency tests are skipped. Generated artifacts stay outside
the checkout, under `.sun/cache/git/builds` (or `SUN_GIT_CACHE`).

For host tools, a build step starting with `"${example/ui}/bin/viewc"` resolves
that dependency for the host even when the consumer targets another platform.

The top-level `packages` array still defines distribution archives. It is
separate from a Git dependency's nested `packages` dictionary.

Configured dependencies select products by entrypoint name, not by manifest ID.
A local dependency can use
`{"package": "example/core", "entrypoints": ["core"]}` to select products from
an included project.

To build one source file with the consumer's settings, use `package`, `git`,
`version`, and `"path": "src/mylib.sun"`. This separate form ignores the
repository's config and exposes `lib/mylib.moon` under `${example/mylib}`.
It cannot be combined with `config` or `packages`.

`version` is a branch, tag, or commit. HTTPS, `ssh://` URLs, and `git@host:path`
SSH addresses are supported, using Git's normal authentication. Sources stay
cached until a build uses `--refresh-sources`. See the
[Git library example](https://github.com/namo-robotics/sun/tree/main/examples/100-git_library)
for a complete project building `sun_serve` from scratch.


### Dependency cache

```text
workspace/
  sun-config.json
  .sun/cache/dependencies/
```

Sun uses the selected workspace's cache. A standalone project uses the directory
beside its config file. It does not need a writable home directory.

To choose a different cache:

```sh
SUN_DEPENDENCY_CACHE=/path/to/shared-cache sun build
```

## Composed config builds

Sun discovers `sun-config.json` beside source files and in parent directories;
`"root": true` stops the parent search. Paths are relative to the declaring
config, and explicit `--path-var` arguments override configured variables.

```json filename="sun-config.json"
{
  "root": true,
  "projects": ["src/*/sun-config.json"]
}
```

This workspace includes the matching project configs. Paths are relative to the
config declaring them; Sun does not automatically search every subdirectory.

A project limited to particular platforms declares `supported_targets`:

```json
{
  "supported_targets": ["x86_64-linux-gnu", "x86_64-linux-musl"]
}
```

Sun compares these targets with `--target`, or the host target when omitted.
Config builds warn and skip incompatible projects before resolving their paths,
dependencies, or included projects. A build containing only skipped projects
succeeds; an explicitly requested package or entrypoint must still match a build
product. Omit `supported_targets` to allow every target; an empty list disables
the project for every target. Target aliases are normalized, while architecture
and ABI remain distinct. Target-specific settings alone do not restrict project
support, and missing dependencies on a supported target remain errors.

A project declares its identity and products:

```json filename="src/shapes/sun-config.json"
{
  "package_id": "example/shapes",
  "entrypoints": [
    { "name": "shapes", "path": "shapes.sun", "type": "library", "export": true }
  ]
}
```

A dependency on `example/shapes` now uses this local project before trying its
download URL. A failed local build is an error, not a reason to download instead.
Package IDs must be unique. Use path-like names such as `example/shapes` without
spaces or `..` components.

```sh
sun build
sun build --package example/shapes
sun build --package example/shapes --entrypoint shapes
```

These build the workspace, one package, or one product. `sun -c sun-config.json`
also builds a config.

### Target-specific settings

Each setting can choose a value independently for each target. An ordinary
value is an unconditional default; a wrapper supplies replacements:

```json
{
  "sun_path": {
    "default": ["build"],
    "target": { "aarch64-linux-gnu": ["build/arm64"] }
  },
  "path_variables": {
    "OPENSSL_LIBS": {
      "default": "vendor/openssl",
      "target": { "aarch64-linux-gnu": "vendor/openssl/arm64" }
    }
  },
  "entrypoints": [
    {
      "name": "app",
      "path": "app/main.sun",
      "type": "binary",
      "output_name": {
        "default": "build/app",
        "target": { "aarch64-linux-gnu": "build/arm64/app" }
      }
    },
    {
      "name": "helper",
      "enabled": {
        "default": false,
        "target": { "aarch64-linux-gnu": true }
      },
      "path": "app/helper.sun"
    }
  ]
}
```

A matching target replaces the default, including entire arrays. Without a
match, the default applies; a wrapper with neither is an error when needed.
Entrypoints and packages default to enabled. Disabled entries skip resolution
of their other settings. Names stay fixed; other entrypoint and package fields
can use wrappers, including resource lists. Do not wrap the structural
`entrypoints`, `packages`, or `dependencies` collections.

Legacy top-level `target` blocks remain supported, but cannot overlap wrappers
for the same setting. Prefer per-setting values to avoid repeating entrypoints.

Use `--target` to select a compilation target and `--no-test` to omit test
binaries. `c_bindings` can generate sources from C headers before compilation;
see [C header binding generation](/c-ffi#optional-header-binding-generation).

### Output paths

```sh
sun describe --field build_root
sun describe --field install_root
sun describe --field package_id
```

Use these commands in scripts instead of guessing paths. Add `--config` and
`--package` to select a project. Without `--field`, `sun describe` prints JSON.

Build files go under `.sun/build/`; installed products go under `.sun/install/`.
Both paths include the target, build configuration, and project name.
`SUN_BUILD` and `SUN_INSTALL` expose the current project's paths to build scripts.

An entrypoint named `shapes` produces `shapes.moon` for a library, `shapes` for a
binary, and `shapes_test` for tests. Without `name`, Sun uses the source filename
without its extension. Manifest IDs do not set these filenames.

### Custom build scripts

```json
{
  "entrypoints": [
    {
      "name": "app",
      "path": "main.sun",
      "build": ["scripts/generate.sh", "scripts/compile.sh"]
    }
  ]
}
```

Sun runs these executable scripts in order from the config directory. Each needs
a shebang. A failure stops the build and preserves the previous installation.
Scripts run on every requested build and must refresh their own generated files.

```sh filename="scripts/compile.sh"
#!/bin/sh
# Compile the selected product with Sun's resolved build settings.
set -eu
"$SUN_EXECUTABLE" build-compile
```

`build-compile` keeps the selected target, compiler options, dependencies, and
output paths. Add native flags when needed:

```sh
"$SUN_EXECUTABLE" build-compile --dynamic -lm
```

Scripts receive `SUN_SOURCE`, `SUN_OUTPUT`, `SUN_TEST_OUTPUT`, `SUN_TARGET`,
`SUN_BUILD`, `SUN_INSTALL`, `SUN_JOBS`, and `SUN_EXECUTABLE`.
`SUN_BUILD_CONTEXT` points to their read-only build settings.

To find a resolved dependency inside a script:

```sh
"$SUN_EXECUTABLE" dependency-path example/shapes
"$SUN_EXECUTABLE" dependency-path example/tools --host
```

`--host` selects tools that run on the build machine when cross-compiling.
These commands read the build context; they do not download or build anything.

Custom `build` replaces normal compilation. Do not combine it with `steps`,
`compile_args`, `pkg_config`, `link_args`, or a Git entrypoint.

### Preparation steps

```json
{
  "steps": [
    {
      "name": "generate",
      "command": ["python3", "generate.py", "${SUN_BUILD}/generated.sun"],
      "inputs": ["generate.py"],
      "outputs": ["${SUN_BUILD}/generated.sun"]
    }
  ],
  "entrypoints": [
    { "name": "app", "path": "main.sun", "steps": ["generate"] }
  ]
}
```

The step runs before normal compilation and reruns when its inputs or tools
change. Outputs must be under `SUN_BUILD`. Commands are argument lists, not shell
expressions. Use `requires` to name earlier steps.

Entrypoints can also use `requires` to build other local entrypoints first.
For native libraries, add `compile_args` and `pkg_config` to the entrypoint.

### Inspect a dependency

```sh
sun resolve --config sun-config.json --package example/app --dependency example/shapes
```

This prints the resolved root and target as JSON. Resolving a local dependency
may build it. The language server uses already staged products and does not run
build commands during discovery.

## Distributions and resources

```json filename="sun-config.json"
{
  "entrypoints": [
    { "name": "app", "path": "main.sun", "type": "binary" }
  ],
  "packages": [
    {
      "name": "app-tools",
      "entrypoints": ["app"],
      "resources": [
        { "path": "assets", "destination": "share/app/assets" }
      ]
    }
  ]
}
```

```sh
sun -c sun-config.json
```

This creates `packages/app-tools/` and `packages/app-tools.tar.gz` under
`SUN_BUILD`. The package contains `bin/app`, the assets, and a `package.json`
inventory. Libraries go under `lib/`. Tests and compiler temporary files stay out.

Resource paths start at the config directory. Destinations must stay inside the
package. Sun rejects missing files, links, and conflicting destinations. Changing
only resources repackages without recompiling unchanged code.

Entrypoint `resources` are copied beside the executable or library in builds,
installs, and packages. `path` is config-relative; `destination` is relative to
that product's directory:

```json
{
  "entrypoints": [
    {
      "name": "app",
      "path": "main.sun",
      "resources": [
        { "path": "assets/icons", "destination": "app.icons" }
      ]
    }
  ]
}
```

Package `resources` and config-wide `exports` use package-relative destinations.

## Building only what changed

```sh
sun --emit-moon -o shapes.moon shapes.sun
sun --emit-moon -o shapes.moon shapes.sun  # Up to date
sun --emit-moon --force-rebuild -o shapes.moon shapes.sun
```

Sun compares inputs, dependencies, target, flags, and compiler before rebuilding.
Unchanged outputs keep their timestamps. `--force-rebuild` skips this check.
Editing a test-only file rebuilds the tests without rebuilding the application.

## Installed libraries

```sun
manifest {
    libraries: ["stdlib.moon", "tls.moon"]
}
```

`stdlib.moon` provides the [standard library](/stdlib). Add `tls.moon` for
[TLS and HTTPS](/tls); it carries its OpenSSL dependency.

The compiler searches its installation directories automatically. For your own
bundles, keep them beside the project or use `--lib-path`.

### Cross-compiling

```sh
sun --emit-obj --target aarch64-linux-gnu \
    --lib-path vendor/aarch64-linux-gnu main.sun
```

Use bundles built for the requested target and a compatible compiler. Sun rejects
wrong-target bundles. Installation directories are searched for target-specific
subdirectories automatically; custom search paths must name the right directory.

See [target-specific settings](#target-specific-settings)
for config builds.

## Exporting complete LLVM IR

```sh
sun --emit-llvm -O0 -o main.ll main.sun
```

This writes LLVM IR, including imported code, without linking or running tests.
Omit `-O0` for optimized output. Use matching LLVM tools to process the result.
This option is for a source entrypoint, not a config build.
