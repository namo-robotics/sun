# Code Generation

The codegen stage walks the analyzed AST and emits LLVM IR. It relies entirely
on the types and annotations stamped by the semantic analyzer — by this point
every expression already knows its resolved `sun::Type`, and generic
specializations have been recorded for it to emit as ordinary non-generic code.

## Structure

`CodegenVisitor` (`codegen_visitor.h`) walks the AST and dispatches. It does
little emitting of its own: nine components do that work, each with its own
header under `include/codegen/` and each owning the state it needs.

They all share one `CodegenState` by reference — the module, the type registry,
the Sun-to-LLVM type resolver, DWARF emission, and the frame currently being
emitted. Where a component needs another, it reaches back through the visitor.
This is the same shape the semantic analyzer uses with `SemanticContext`.

| Component | What it owns |
|-----------|--------------|
| `CodegenState` | The module, type registry, type resolver, DWARF, current frame |
| `ScopeManager` | The scope stack, and every drop it has to emit |
| `FunctionRegistry` | Calling conventions, where each function came from, name lookup |
| `ClassGenerator` | Classes, interfaces, enums, generic instantiation, vtables |
| `FunctionGenerator` | Functions, lambdas, closures, returns |
| `VariableGenerator` | Variables, lvalues, globals |
| `LoopGenerator` | Loops, and the jumps out of them |
| `ErrorGenerator` | `throw`, `try`/`catch`, and every call that may unwind |
| `IntrinsicsGenerator` | Compiler intrinsics and libc built-ins |

Rules that need no codegen state are free functions instead, so other passes can
reach the same answers: `sun::codegen::ops` (`support/scalar_ops.h`) for scalar
widening and coercion, and `sun::codegen::layout` (`support/struct_access.h`) for
field addresses, alignment and slot writes.

## Key Conventions

- LLVM is accessed through a shared context: `ctx.builder` and `ctx.context`.
- Sun types map to LLVM types via the type resolver:
  `typeResolver.resolve(type)` for variables and
  `typeResolver.resolveForReturn(type)` for function returns.
- Classes are value types: functions returning a class return the struct by
  value, and callers materialize it on the stack for addressability.
- Arrays are fat pointers: `{ ptr data, i32 ndims, ptr dims }`.
- Throwing functions (`T throws IError`) return plain `T`; errors are native LLVM
  exceptions (`__gxx_personality_v0`, landing pads), so `throw` unwinds and
  `catch` selects a handler by the thrown class's type id.
- Lambdas use closure structs; named functions use direct calls. Class methods
  use the closure ABI: arg 0 is a ptr to `{ ptr func, ptr env }` with the
  receiver in `env`, and `obj.method` in value position is a lambda-typed bound
  method `{ methodFn, objPtr }`.
- C extern globals are emitted as external-linkage LLVM globals with no
  initializer. `ExternCEmitter` owns the resolved Sun-name to native-symbol
  map used by loads, assignments, lvalues, module members, and function-pointer
  calls. A `sun.cabi` metadata tag keeps the native name unchanged when
  `.moon` bundling prefixes or remaps Sun symbols.
- Before emitting any body, `FunctionGenerator::declareBlockSignatures` walks
  the complete module subtree and declares every free function and class
  method. Included files are one merged AST even when their declarations sit
  under separate module nodes, so calls do not depend on source-list order.
  Re-entering a module during emission reuses those declarations rather than
  creating new ones.
- Call arguments are never re-examined here. Semantic analysis records an
  `ArgConversion` per argument on the call node, and every kind of call — plain,
  module-qualified, generic, method, lambda, interface, constructor,
  extern "C" — lowers its arguments through one loop, `emitCallArguments`, that
  switches on those tags (take the address for a borrow, zero the source for a
  move, build a fat pointer for an interface, extend a number, ...). Codegen
  does no semantic analysis of its own.

## Source Layout

`include/codegen/` and `src/codegen/` share one layout: a folder per component,
holding both its header and the sources that implement it.

| Folder | Holds |
|--------|-------|
| *(top level)* | `codegen_visitor`, `codegen_state`, `llvm_type_resolver`, `debug_info_builder` |
| `scopes/` | The scope stack and the drop code it emits |
| `classes/` | Class and interface definitions, members, method bodies, enums, vtables |
| `functions/` | Functions, lambdas, closures, returns, the function registry |
| `variables/` | Declarations, loads, assignments, lvalues, global initialization |
| `expressions/` | Calls, arrays and indexing, conditionals, match, blocks |
| `loops/` | `for`, `while` and `for-in`, and the jumps out of them |
| `errors/` | `try`/`catch`/`throw` and unwinding calls |
| `support/` | Helpers holding no codegen state: type checks, scalar ops, field access |
| `abi/` | The C boundary: per-target ABI classification (x86-64 SysV; AArch64 AAPCS64, ELF and Darwin variants) and the extern "C" emitter |
| `intrinsics/` | Compiler intrinsics and libc built-ins, by area, plus thread support |

Each component's `*_generator.cpp` holds only the forwarders it uses to reach
the rest of codegen; those cannot be inline in the headers, because the headers
are included by `codegen_visitor.h`.

## Adding a New Expression Type

1. Add an `ASTNodeType` enum value and AST class.
2. Implement a `codegen` method on the component that owns that kind of node,
   or on `CodegenVisitor` if it belongs to none.
3. Update the `codegenExpression()` dispatch switch to route to it.

A component that emits sub-expressions declares two forwarders,
`codegen(const ExprAST&)` and `codegen(const BlockExprAST&)`. The block overload
is not optional: without it a block binds to the `ExprAST` one, which attaches an
expression debug location and changes the DWARF output. A deleted template
overload alongside them turns a missing overload into a compile error rather than
infinite recursion.
