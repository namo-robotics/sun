# Function Calls

Part of the [Sun ABI draft](/abi). These are proposed requirements, not guarantees
of current releases. Open decisions must be resolved before stabilization.

## Function calls

Signature lowering translates a Sun function signature into machine arguments,
results, and calling rules.

| Subject | Level | Requirement |
| --- | --- | --- |
| Shared procedure | MUST | Use one defined lowering procedure for definitions, declarations, direct and indirect calls, interface methods, callbacks, and returns. |
| Argument order | MUST | Specify the order of parameters, including receivers, closure arguments, and result-storage arguments. |
| Scalars | MUST | Specify scalar extension rules and Boolean handling. |
| Aggregates | MUST | Specify whether each value is passed directly, split into scalars, or passed through storage. |
| Indirect storage | MUST | Specify alignment and aliasing rules for arguments and results. |
| Empty values and parameter packs | MUST | Specify how empty parameters and results are passed and how specialized parameter packs expand. |
| Ownership | MUST | Define ownership and lifetimes on normal and exceptional exits, including who owns caller-provided storage. |
| Target convention | MUST | Specify the calling convention and all function attributes that affect the ABI. |
| Indirect passing | MUST NOT | Introduce an implicit Sun copy or a hidden heap allocation. |

## Proposed implementation

Add a Sun signature-lowering layer alongside the C ABI layer. Describe the Sun
passing rules first, then translate them into LLVM types and attributes.
Caller-provided storage can hold a moved argument or return value.

## Open decisions

Choose aggregate passing rules for each initial CPU target. Options include
platform C rules applied to lowered Sun types, or a Sun convention that passes
aggregates through storage. This draft chooses neither. LLVM structure types
alone do not specify how machine code passes values.
