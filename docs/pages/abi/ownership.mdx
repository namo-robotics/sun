# Ownership & Allocation

Part of the [Sun ABI draft](/abi). These are proposed requirements, not guarantees
of current releases. Open decisions must be resolved before stabilization.

## Ownership, borrowing, and allocation

Moving bits does not grant permission to copy ownership. Destroying a value and
freeing its storage are separate operations.

| Subject | Level | Requirement |
| --- | --- | --- |
| Copies | MUST NOT | Introduce implicit Sun copies across a compiled boundary. |
| Ownership transfer | MUST | Leave exactly one owner responsible for cleanup after a successful transfer. |
| Failed calls | MUST | Define the transfer point and cleanup responsibility if argument evaluation, construction, or the call fails. |
| Partial initialization | MUST | Destroy only the parts that were initialized. |
| Borrow metadata | MUST | Preserve mutability, lifetime relationships, and aliasing constraints needed for safety checks. A machine pointer alone is insufficient. |
| Borrow optimization | MUST NOT | Give the producer and consumer conflicting optimizer assumptions about the same borrowed storage. |
| Deallocation | MUST | Use a compatible deallocation operation with the required alignment and allocator state. |
| Runtime lifetime | MUST | Keep destruction and deallocation services available for the allocation's lifetime. |

For example, `Unique<T>` currently stores a pointer, destroys `T`, and then calls
`_free`. It stores no allocator identity. Passing it across a boundary requires
compatible allocation and free operations; matching pointer layouts do not make
custom allocators interchangeable.

## Open decisions

Specify transfer and failure rules for each parameter mode, construction,
return, and cleanup path. Define the system allocator contract and runtime
linkage rules before promising ownership compatibility across compiler versions.
