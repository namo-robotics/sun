# Compatibility Model

Part of the [Sun ABI draft](/abi). These are proposed requirements, not guarantees
of current releases. Open decisions must be resolved before stabilization.

## Compatibility model

Compatibility depends on the contracts a bundle needs and the implementations a
consumer provides. A compiler version identifies who built the bundle; it does
not decide whether the bundle can be imported. Compatibility has a direction and
a target: compiler A accepting B's output does not mean B accepts A's output.

Each bundle describes these requirements. Field encodings are still undecided.

| Requirement | Contents |
| --- | --- |
| Producer identity | Exact compiler build and reproducible release ordering, for diagnostics |
| Container format | Rules for locating and decoding sections |
| Interface schema | Encoding of declarations, types, ownership, and references |
| Generic semantics revision | Rules for interpreting and specializing exported generic bodies |
| Sun ABI revision | Layout, call, identity, and ownership rules at compiled boundaries |
| Target profile | Architecture, byte order, pointer model, platform ABI, and data layout |
| Runtime requirements | Required runtime interfaces and compatible revisions |
| Required capabilities | Features the consumer needs to understand |
| Payload requirements | Object or LLVM bitcode format and required CPU features |
| Artifact and dependency identities | Exact declarations and dependencies used by the bundle |

| Subject | Level | Requirement |
| --- | --- | --- |
| Bundle metadata | MUST | Describe every requirement listed above. |
| Compiler versions | MUST NOT | Authorize an import from version numbers, a compiler-version table, or a human compatibility declaration. |
| Format and ABI | MUST NOT | Treat a format change as an automatic ABI change, or vice versa. |
| Unknown metadata | MUST | Ignore unknown metadata only when the schema marks it optional; reject unknown required capabilities. |
| Validation timing | MUST | Check compatibility before using imported layouts or emitting calls. |
| Dependencies | MUST | Check all reachable bundled dependencies, including transitive dependencies. |
| Unsupported combinations | MUST | Report a compilation error naming the artifact and unmet requirement. |
| Target matching | MUST | Apply defined target-profile compatibility rules, rather than compare architecture and OS names or raw target triples. |

A reader can support several format or ABI revisions. Decoding a bundle does not
prove that its semantics or ABI are compatible. Different target triple spellings
can describe equivalent targets; the same architecture can have incompatible
runtime environments, CPU features, or ABI options.

## Automatic compatibility decision

The producer records the contracts used during compilation. The consumer compares
them with contracts supported by its installed implementations. Supporting an old
contract requires working code, such as a retained decoder or lowering path.

| Manifest | Level | Required contents |
| --- | --- | --- |
| Producer: layouts | MUST | Canonical size, alignment, offsets, discriminants, valid representations, and referenced nominal identities. |
| Producer: calls | MUST | Lowered signatures, calling conventions, attributes, ownership transfer modes, and indirect-call contracts. |
| Producer: runtime | MUST | Required symbols and their structure and behavior. |
| Producer: readers and semantics | MUST | Required format decoders, generic semantics, intrinsic behavior, target features, and payload readers. |
| Producer: dependencies | MUST | Exact dependencies and contracts used by compiled code or exported generic bodies, including private declarations those bodies use. |
| Producer: source of truth | MUST | Derive the manifest from contracts actually used by code generation. A separate handwritten description is insufficient. |
| Consumer | MUST | Derive supported contracts from the decoders, lowering code, runtime implementations, and generic interpreters it ships. |
| Contract identifiers | MUST NOT | Use manually bumped revisions as compatibility promises. |
| Canonical encoding | MUST | Preserve meaningful order and identities; exclude incidental paths, timestamps, traversal order, and other irrelevant build data. |

Contract identifiers are derived from canonical descriptions. Where a description
cannot fully express behavior, the design uses implementation fingerprints as
explained below.

| Step | Level | Consumer action |
| --- | --- | --- |
| 1. Decode | MUST | Read and validate requirements with a supported decoder. |
| 2. Expand | MUST | Collect requirements from reachable dependencies and exported generic bodies, keeping exact artifact identities. |
| 3. Resolve | MUST | Find an implementation and target capability for each requirement. All required capabilities must be available. |
| 4. Compare structure | MUST | Compare canonical structural contracts exactly and apply target-profile compatibility rules. |
| 5. Compare behavior | MUST | Require matching semantic contracts or a retained implementation of the producer's contract. |
| 6. Decide | MUST | Accept only if every requirement is satisfied. Otherwise report a useful mismatch and fail compilation with a nonzero exit status. |
| Cache key | MUST | Include artifact identity, consumer contract identity, target profile, and relevant build options. |
| Cache reuse | MUST NOT | Reuse a compatibility result after any key input changes, or skip validation because another bundle from the same producer passed. |

Digests can index and cache contracts. Hashing the entire compiler executable is
too broad: an optimizer change need not affect the ABI. Layout checks alone are
too narrow: identical layouts can have different cleanup or exception behavior.

## Computed ABI hashes

The proposed ABI identifier hashes a contract, rather than a release number or
compiler binary. SHA-256 is the proposed algorithm:

```text
contract_hash = SHA256(canonical_encode(
    domain = "sun.abi.contract",
    encoding_schema,
    contract_kind,
    effective_target_properties,
    contract_description
))

requirements_hash = SHA256(canonical_encode(
    domain = "sun.abi.requirements",
    encoding_schema,
    sorted_required_contract_keys_and_hashes
))
```

These expressions list inputs; they do not specify a byte encoding. Each layout,
call signature, runtime service, and semantic contract has its own hash. A bundle
also has an aggregate requirements hash for indexing and caching.

| Subject | Level | Requirement |
| --- | --- | --- |
| Encoding | MUST | Define unambiguous field tags, lengths, integer representation, ordering, defaults, and schema identification. |
| Encoding shortcuts | MUST NOT | Use raw C++ memory or incidental protobuf serialization bytes as canonical encoding. |
| Descriptions | MUST | Keep the underlying contracts so errors can report a changed field offset instead of just different hashes. |
| Imported declarations | MUST | Derive each contract with supported lowering code, or use a retained implementation that honors the producer's description. |
| Hash verification | MUST NOT | Simply trust and echo the bundle's hash. |
| Recursive types | MUST | Use stable declaration references and a canonical graph encoding, rather than expand pointee layouts indefinitely. |
| Equal hashes | MUST NOT | Erase nominal identity or replace validation of referenced contracts. |

A class contract includes nominal identity, field layouts and offsets, size,
alignment, and valid representations. A call contract includes parameter and
result lowering, hidden parameters, register or indirect passing, extension and
aliasing rules, and ownership. Interface slots, closure calls, error propagation,
and runtime operations also need contracts.

User-defined types are checked on import; the compiler cannot precompute hashes
for future types. The recursive graph encoding still needs a specification.

An aggregate requirements hash can differ from the consumer's aggregate hash
without a conflict: the consumer may support more contracts than the bundle
needs. Each required contract is checked separately.

| Change | Expected decision |
| --- | --- |
| Optimizer changes but boundary contracts stay the same | Same required hashes; accept if other checks pass |
| Consumer adds a type or calling convention | Existing requirements can still be satisfied |
| Required field offset or argument-passing rule changes | Reject unless the consumer supports the old contract |
| Cleanup behavior changes but layout stays the same | Check the changed semantic contract; matching layouts are insufficient |
| Diagnostic wording changes | No ABI contract change |

Equal contracts can occur in different compiler releases. Hashes do not order
releases; producer metadata controls the age warning below. Changing the hash
algorithm or schema requires decoder support or migration.

## Semantic fingerprints and conservative rejection

No general algorithm can prove that arbitrary compiler implementations behave
identically. The compatibility check accepts defined, supported contracts and
rejects combinations it cannot verify.

For behavior not fully described by a contract, the proposed fallback hashes the
responsible implementation, all implementation dependencies, relevant
configuration, and tools that affect its behavior. This can reject a harmless
refactor. More precise contracts and retained implementations can reduce those
rejections.

| Subject | Level | Requirement |
| --- | --- | --- |
| Changed fingerprint | MUST | Reject it unless the consumer retains an implementation of the original contract. |
| Manual overrides | MUST NOT | Bypass rejection by updating an expected hash or declaring a release compatible. |
| Fingerprint coverage | MUST NOT | Hash a selected source file while omitting helpers or configuration that affect its behavior. |
| Unknown dependencies | MUST | Include more inputs conservatively, or leave the feature unsupported, when the complete implementation dependency set cannot be established. |
| Compatibility tests | MUST NOT | Use passing tests alone to authorize an unsupported semantic contract. |

Tests catch missing contract details but do not prove equivalence for all
programs. The design assumes the producer follows the contracts; it does not
prove that arbitrary supplied machine code obeys its manifest.

## Warnings and errors

Check compatibility before deciding whether to warn about compiler age. Apply
this policy to direct and transitive compiled dependencies, including code
embedded in another bundle.

| Compatibility result | Producer | Required action (MUST) |
| --- | --- | --- |
| All requirements satisfied | Older compiler | Warn and continue. |
| All requirements satisfied | Same compiler build | Continue without an age warning. |
| All requirements satisfied | Newer compiler | Continue; age alone does not imply incompatibility. |
| All requirements satisfied | Different build, unknown ordering | Warn that ordering is unknown and continue. |
| Mismatch or unverifiable compatibility | Any compiler | Report an error and terminate compilation with a nonzero status. |

| Subject | Level | Requirement |
| --- | --- | --- |
| Diagnostic order | MUST | Finish compatibility validation before deciding on an age warning. |
| Age warning | MUST | Name the artifact and both compiler builds, and state that compatibility checks passed. |
| Duplicate warnings | MUST NOT | Emit more than one age warning per exact dependency artifact per compilation. |
| Compatibility error | MUST | Identify the failing contract and, when relevant, the dependency path that introduced it. |
| Error detail | MUST NOT | Report only that compiler versions differ. |
| Failed compilation | MUST NOT | Run or publish an executable as a successful compilation result. |
| Official build ordering | SHOULD | Use an ordered release identifier generated by release automation. |
| Local timestamps | MUST NOT | Use them to establish compiler age. |
| Legacy bundles | MUST | Reject bundles missing contract information as “compatibility cannot be established”, unless a supported legacy decoder can reliably derive every missing requirement. |
| Legacy format number | MUST NOT | Use an old Moon format number as evidence of compatibility. |

Development builds can use recorded source ancestry for age ordering. Divergent
histories or missing provenance have unknown ordering. Neither release order nor
ancestry authorizes an import.

Example diagnostics:

```text
warning: dependency geometry.moon was produced by an older Sun compiler
  producer: <producer build identity>
  consumer: <consumer build identity>
  required contracts verified; continuing

error: dependency geometry.moon is incompatible with this compilation
  contract: layout of geometry.Point
  dependency requires: size 24, alignment 8
  available lowering: size 32, alignment 16
  compilation stopped
```
