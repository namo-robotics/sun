# Conformance & Implementation

Part of the [Sun ABI draft](/abi). These are proposed requirements, not guarantees
of current releases. Open decisions must be resolved before stabilization.

## Implementation baseline and release criteria

The compiler currently has portable declaration keys, C ABI lowering, serialized
Moon declarations and generic bodies, and a single Moon format-version check.
The linker checks architecture and OS family. These cover only part of this draft.

Relevant code is in `src/semantic_analysis/portable_declaration_key.cpp`,
`src/codegen/llvm_type_resolver.cpp`, `src/codegen/functions/functions_lambdas.cpp`,
`src/codegen/abi/`, `include/moon_bundling/moon.proto`, and
`src/moon_bundling/module_linker.cpp`. See [Code Generation](/architecture/codegen).

| Subject | Level | Requirement |
| --- | --- | --- |
| Stable revision | MUST NOT | Declare stability before supported targets, all reachable type categories, call lowering, ownership, symbols, and runtime contracts have precise definitions and compatibility tests. |
| Unsupported categories | MUST | Reject them with a diagnostic. |
| Historical artifacts | MUST | Test real artifacts built by older compiler releases. Rebuilding both sides with the new compiler does not test compatibility with old output. |
| ABI changes | MUST | Detect changes through generated contracts and regression checks. An unchanged version number is insufficient. |
| Passing tests | MUST NOT | Override an unsupported contract. |

## Required test coverage

The suite must cover every row below. Saved layout and signature fixtures
supplement executable tests.

| Area | Level | Cases |
| --- | --- | --- |
| Dependency graphs | MUST | Old producer with new consumer; transitive and diamond dependencies. |
| Values and calls | MUST | Scalar and aggregate arguments and returns, enums, arrays, and alignment. |
| Indirect calls | MUST | Closures, interface methods, and callback ownership. |
| Cleanup | MUST | Moves, destruction counts, allocation/free pairing, and exceptional cleanup. |
| Generics | MUST | Old bodies with new concrete types; precompiled specializations; rejection of conflicting specializations. |
| Runtime | MUST | Global initialization, shared state, and supported error propagation. |
| Unsupported inputs | MUST | Reject incompatible targets, formats, ABI revisions, and capabilities. |
| Toolchain changes | MUST | Supported optimization levels and LLVM upgrades for each target profile. |
| Age warnings | MUST | Warn once per older compatible artifact, including diamond dependencies. |
| Failed validation | MUST | Exit with a nonzero status for incompatible or unverifiable dependencies. |
| Producer ordering | MUST | Newer compatible producers and divergent development-build histories. |
| Contract changes | MUST | Detect structural and semantic changes without manual version bumps; preserve unaffected contracts after unrelated changes. |
| Cached results | MUST | Invalidate after contract, target, artifact, or relevant option changes. |
| Legacy support | MUST | Missing manifests, retained old implementations, and transitive producer metadata. |

## Suggested implementation sequence

1. Audit current representations and runtime calls; choose initial targets.
2. Specify layout and calling-convention algorithms.
3. Centralize Sun lowering and add layout and signature fixtures.
4. Generate manifests and implement validation, warnings, and errors.
5. Define generic compatibility and preserve imported layouts.
6. Add archived cross-version fixtures and publish the supported-contract inventory.
7. Declare a stable revision after meeting the release criteria.

Library replacement, layouts that can change without recompiling consumers, and
runtime type-erased generics remain separate proposals. Swift's
[library evolution](https://www.swift.org/blog/library-evolution/) documentation
describes the additional guarantees and costs of library replacement.
