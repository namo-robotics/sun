# Error Handling

Sun reports recoverable failures with exceptions. A throwing function returns its
ordinary success value and declares `throws`. Callers either propagate the
exception with their own `throws` declaration or handle it in a `try` block.
There are no result wrappers or prefix `try` expressions.

## Declaring and handling exceptions

```sun
/** Groups failures from storage operations. */
exception StorageFailure {}

/** Carries the failing device's numeric status. */
exception DeviceFailure extends StorageFailure {
  var code: i32;
}

/** Returns a value or propagates a bounded exception. */
function read_value(ready: bool) i32 throws {
  if (not ready) {
    var error: DeviceFailure = {code: 7};
    throw error;
  }
  return 42;
}

/** Handles every exception in the storage family. */
function main() i32 {
  try {
    return read_value(false);
  } catch (error: StorageFailure) {
    return 1;
  }
}
```

Catch clauses are considered in source order. A concrete catch can access that
exception's fields. A family catch accepts every descendant, and `catch { ... }`
accepts any Sun exception. Exception parents must be fieldless.

Inside a handler, `throw;` rethrows the active exception. `throw error;` also
preserves its concrete type, including through a family catch. Catch bindings
can be inspected, borrowed, and have individual fields changed. They cannot be
moved into another variable or replaced as a whole: a family binding may refer
to a larger concrete value.

## Exception storage

Every exception fits in a fixed inline payload of at most 128 bytes, including
field padding. Numeric values, booleans, characters, plain enums, and fixed-size
arrays of these types are supported. References, pointers, owning objects,
variable-sized arrays, generic exception declarations, and exception destructors
are rejected. Constructors, methods, and interfaces are supported; fields
inherited from an interface must satisfy the same storage restrictions.

The transport reserves equally sized records regardless of the concrete payload.
Throwing copies the bounded payload into this storage without heap allocation.
Objects in unwound scopes are destroyed. If a constructor throws, its initialized
fields are destroyed, but the incomplete object's destructor is not called.
Destructors may catch exceptions internally; they cannot propagate exceptions.

## Standard-library errors

Standard-library operations return ordinary values and throw concrete exceptions.
For example, checked indexing throws `IndexOutOfBoundsError`; allocation failure
throws `AllocationError`. `Error` carries a numeric code and up to 96 bytes of
inline diagnostic text. Text supplied by a literal or a `String` is copied and
truncated without allocating. The original string can then be destroyed safely.
TLS errors use the same bounded diagnostic strategy. XML errors reserve separate
bounded storage for a message and filename alongside location information.

`IError` provides borrowed access to `code()` and `message()`. It is an interface,
not an exception family: catch a concrete exception or a declared exception
parent. Calling `message()` explicitly creates an owned `String` and can throw
on allocation failure. Diagnostic allocation is separate from throwing.

```sun
using std;

/** Handles an invalid index and explicitly chooses whether to copy its message. */
function report() void throws {
  var values = Vec<i32>(global_allocator, 1);
  try {
    values.get(10);
  } catch (error: IndexOutOfBoundsError) {
    var message = error.message();
    std.io.eprintln(message);
  }
}
```

Readiness and absence remain ordinary values. For example, `Option<T>` represents
an optional value, and nonblocking I/O distinguishes completion from “would block.”
A failed write throws `std.io.WriteError`; its `transferred()` method reports bytes
already written, so a retry can start at the remaining suffix.

Tests return `void` and can throw by default. Assertion failures are exceptions.
A throwing `main` can propagate exceptions to the process boundary, which prints
a fixed diagnostic and exits with status 1 after stack cleanup. Worker threads
must handle their exceptions before returning from the thread body.

## Migrating from returned errors

- Change `Result<T>` and other error-wrapper return types to `T throws`.
- Replace `return Result.Ok(value)` with `return value` and error variants with
  `throw error`.
- Replace `try operation()` with an ordinary call in a throwing function, or a
  block-form `try` with catches.
- Replace matches on error variants with catches around the operation itself.
- Replace `ignore_error(operation())` with `try { operation(); } catch {}` only
  when deliberately discarding every failure.
- Give fallible constructors `init(...) throws`; successful construction needs
  no returned status.

`_Result`, standard-library error-wrapper enums, and prefix `try` are removed.
Ordinary user enums and typed enum matching remain available.

## Native transport and JIT registration

Exception declarations and handler bodies survive Moon serialization. Bundles
using this transport declare the `sun.exceptions.bounded` ABI rule. Concrete
identities include declaration identity and layout; matching does not depend on
descriptor addresses across modules. Rebuild bundles compiled with returned-error
APIs before importing them into migrated code.

The implementation uses the Itanium base unwinder with a Sun personality and
Sun-owned bounded storage. It does not call the C++ exception allocator.
Each thread initializes a base propagation record. Exceptional cleanup selects
a separate record in its own stack frame for internally handled failures,
then restores the previous throw target before resuming the original unwind.
A termination handler prevents a nested exception from outliving that stack
record. Native unwind headers remain at their original addresses.

Build and run the exception checks from the repository root:

```sh
cmake -S . -B build
cmake --build build --target sun sun_source_exception_tests sun_exception_tests sun_exception_allocation_probe -j$(($(nproc)/2))
SUN_PATH=$PWD ctest --test-dir build -R '^Errors_(NativeExceptions|SourceExceptions)\.' --output-on-failure -j$(($(nproc)/2))
```

On macOS, use half the logical CPU count reported by `sysctl -n hw.logicalcpu`
instead of `nproc`.

**AOT exception transport must not allocate**, including on its first throw
after explicit thread initialization. The AOT probe rejects allocations and
fails if any are attempted, even when propagation still completes.

**JIT registration eagerly prepares unwind lookup indexes.** After JITLink
relocates a module's frame descriptions, the registrar parses every frame and
calls the platform's `_Unwind_Find_FDE` lookup before the module becomes
callable. Preparation may allocate; it does not execute a warm-up throw.
Missing lookup support, malformed frame data, or a failed frame lookup rejects
materialization. Failed lookup also removes the new frame registration.

The JIT probes now reject allocations during transport too. They cover first
throws, independently loaded modules, removal and reloading, and concurrent
throws after registration. Compiler-generated `DW.ref` personality pointer
cells remain local to each module so unloading one does not invalidate another
module's unwind metadata. Native frame deregistration releases indexes before
the code is unmapped. Exception values retain fixed thread-local and stack
storage in both execution modes.

There are limits to the JIT guarantee. `_Unwind_Find_FDE` is a platform extension,
and libgcc can silently fall back to linear lookup when preparation runs out of
memory. Successful lookup alone cannot certify that its index allocation
succeeded. Registration racing with an unwind in another thread is also outside
the allocation-free probes: the platform may expose newly registered tables
before eager indexing completes. JIT throw-time allocations remain permitted
in these cases; the strict AOT requirement is unchanged.

The compiler embeds the runtime archive for its host architecture and operating
system. Native linking extracts a temporary copy and removes it when linking
finishes; compiler installations need no separate Sun runtime archive.
Cross-target Moon bundles and object files support x86-64 and AArch64 Linux and Darwin; linking an executable requires
a matching runtime archive. Linux x86-64 has been validated locally; macOS
Apple Silicon validation has not been run locally. Passing the probes does not replace
auditing the selected unwinder and platform.

The helpers are currently implemented in C++ and compiled without C++ exception
handling or RTTI. The intended follow-up is to generate all Sun-owned exception
helpers as LLVM IR, including the personality function and panic integration;
only the platform unwinder remains external. JIT frame indexing stays in the
compiler. Generated throws initialize the statically reserved thread record
before first use; this selects storage without allocating it.

The libraries have separate responsibilities: `sun_exception_runtime` contains
the transport used by generated programs, while `sun_jit_support` contains
compiler-side frame registration and indexing. The runtime library does not
depend on LLVM or the JIT support library. Test fixtures and allocation
instrumentation live under `tests/`; production JIT interfaces expose no
test-only registrar or lookup injection hooks.
